# 사용자 신고·차단 연결 (SAFE-01/03)

## 기준과 인증 연결 경계

- 작업 시작 시 #47은 OPEN/미병합. 최신 `origin/dev=0671aaa`에서 `feature/front-SAFE-01-03` 분기. AUTH-04 커밋을 복사/병합하지 않음.
- 기존 `readAccessToken()`의 sessionStorage 우선/localStorage 차선 읽기를 재사용. 새 토큰 키/저장소·가짜 사용자 ID·인증 우회 없음.
- `features/safety/auth.ts`는 현재 토큰을 관찰하는 임시 연결 경계. focus/storage/400ms 동기화로 화면을 교체하며 보내기 직전과 응답 시 토큰 일치 확인, 이탈 시 요청 취소. 서버가 학교 인증/팀장/본인 여부를 최종 검사함.
- #47 병합 후 `useSafetyToken`과 토큰 기준 key를 `useAuth`의 session/scope로 교체하고, `ReportAction`/`createBlocksController`의 API 호출을 `store.execute` 및 공통 AbortSignal로 연결할 것. 기존 타인 프로필의 차단 요청도 같은 경계로 교체. 이 브랜치는 공통 인증 전체 구현을 포함하지 않음.

## 화면과 계약

- 기존 타인 프로필의 사유 목록·신고 요청을 `reportTarget`으로 일반화하고 공통 `ReportAction` 폼을 재사용. 기존 차단/해제 API를 유지하고 응답 확인·중복 클릭 방지·취소/늦은 응답 방어를 보완.
- `POST /api/reports`: `targetType`, `targetId`, `reasonCode`, `detail`(선택, 최대 200자). USER=사용자 ID, POST=모집글 ID, APPLICATION=지원 ID. 지원 메시지는 사용자 ID나 역할 ID로 보내지 않음.
- 모집글 상세에서 본인 글이 아닌 실제 모드에 모집글 신고 제공. 기존 상세의 `isMine`이 없거나 공개 조회면 서버의 본인 신고 거절을 안내함. 지원자 관리에서는 서버 `isMine` 확인 후 표시하는 지원 내역에 지원 메시지 신고 제공. mock 모집/지원 화면에서는 실제 신고 폼을 제공하지 않음.
- 신고는 학교 인증 회원만. APPLICATION은 해당 글의 팀장만 가능. 409 ALREADY_REPORTED는 이미 신고됨으로 안내하고 재접수 버튼 비활성화. 401/403·미인증·본인 신고·대상 없음은 성공 처리하지 않음. 응답 유실은 접수 가능성을 안내하고 재전송 시 서버 중복 정책을 따름.
- `/me/blocks`: 내 차단 목록. 설정에서 연결할 경로는 `/me/blocks`. 현재 내 프로필 바로가기에도 링크 추가.
- `GET /api/users/me/blocks?size=20[&cursor=...]`: 응답의 문자열 nextCursor를 그대로 사용. 커서는 차단 레코드 ID이고 항목의 userId로 만들지 않음.
- `DELETE /api/blocks/{userId}`: 해제 확인 후 사용자 ID로 요청. 성공 응답 확인 후 해당 행 제거, 실패 시 행과 더 보기 커서 유지/오류 안내. 401/403은 개인정보 목록 제거. 여러 번 해제해도 서버 결과는 동일.
- 차단 시 양쪽의 PENDING 지원은 마감됨. 차단 해제로 복원되지 않으며 ACCEPTED 팀은 유지됨. 기존 타인 프로필의 차단 확인창에도 안내 추가.

## 검증 결과 (2026-11-17)

- 빌드·lint, `check-safety.mjs`(요청 계약/오류/더 보기/해제 실패·성공/동시 클릭/늦은 응답/권한 오류/정적 렌더), 기존 지원자 관리·모집 화면 회귀 검증. 이 스크립트들은 실제 브라우저 검증이 아님.
- 실제 로컬 백엔드/MySQL/Redis, mock·관리자 예시 OFF로 확인. 기존 로컬 컨테이너·teamup DB·loopback 연결, ddl-auto=validate·정기 배치 OFF를 재확인. 기존 테스트 계정만 재사용. 백엔드 변경 없음.
- 실제 API PASS: POST/모집글 신고 및 APPLICATION/지원 메시지 신고 → 관리자 목록에 정확한 유형·대상으로 표시. 같은 계정의 중복 신고 409, 무토큰 401, 미인증 403, 본인 신고 거절 확인.
- 실제 API PASS: 제3의 테스트 계정으로 차단 2건 생성 → size=1 커서로 두 페이지 조회 → 각 사용자 ID로 해제 → 재조회 시 목록에서 제거/빈 목록 확인. 기존 팀장/지원자 사이의 대기 지원을 마감시키지 않는 조합으로 검증하고 검증용 차단은 해제함.
- 해제 실패 안내·행 보존은 요청 가로채기/Controller 검증으로 확인. 실제 서버 장애를 주입하지 않음.
- 신고 데이터는 로컬에 유지. 계정 정보·토큰·비밀번호·코드·환경·로그·백업은 저장소에 포함하지 않음.
- 화면 클릭, 실제 좁은 화면 배치, 실제 화면에서 계정 전환/로그아웃/권한 오류/차단 해제 실패 표시는 브라우저 미검증. 브라우저 연결 도구는 `The browser access host is unavailable`을 반환함. API 통과로 프론트 전체 통과를 주장하지 않음.

## 브라우저 확인 순서

프론트 `http://localhost:5173`, 백엔드 `http://localhost:8080`. 기존 Git 밖 로그인 정보 파일 사용. #47 미병합 기준이므로 해당 PR의 로그인 상태/로그아웃 보조 버튼은 이 브랜치에 포함되지 않음. 계정 전환은 로그인 화면에서 수행.

1. 지원자로 `/login` → `/posts/{postId}` → 테스트 모집글 신고. 이미 실제 API로 신고한 대상이면 접수 시 중복 안내가 표시됨.
2. 팀장으로 `/login` → `/posts/{postId}/applicants` → 테스트 지원 메시지 신고. 지원 ID가 신고 대상이며, 기존 신고의 중복 안내 확인 가능.
3. 관리자로 `/login` → `/admin/reports` → 모집글/지원 메시지 테스트 신고 2건 확인. 처리 버튼은 누를 필요 없음.
4. 같은 관리자 테스트 계정에서 `/users/{userId}` → 다른 테스트 사용자 차단 확인 → `/me/blocks` → 해제 확인 → 목록에서 제거 확인. 이 계정 조합은 팀장/지원자 사이의 PENDING 지원을 건드리지 않음. 팀장/지원자끼리 차단하면 기존 대기 지원이 마감되므로 그 조합은 상태 변경을 의도할 때만 사용. 구체적인 테스트 대상 ID와 계정 정보는 Git 밖에서 관리.
5. `/me/profile`의 내 차단 목록 링크 확인. 비로그인/만료 상태의 `/me/blocks` 안내 확인. 실제 20개 초과 차단 데이터는 만들지 않았으므로 UI 더 보기는 자동 검증과 실제 API size=1 검증으로 구분됨.
